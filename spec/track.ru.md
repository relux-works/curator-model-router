# Трек: роутинг моделей

Статус: **ЧЕРНОВИК**, 2026-09-23, обновлён 2026-10-01.

**Спецификации:**

- `spec/model-routing.md`: решения R1–R13, с учтённым независимым ревью;
- `spec/evidence-format.md`: формат свидетельств;
- `spec/headroom.md`: факты использования и стратегия `headroom-aware`.

**Роадмап:**

- Этапы A0 и A1 относятся к вехе M4. Половина A0 на стороне task-board — это резолвер выбора агентов; половина на стороне роутера — W0 и W1.
- Доступность по профилям, которую питают записи использования из W3, — это M5b.
- Этапы B–E — это M8.
- Этап K4, термы трека KV-кэша в роутере, — это M8, после K2a (M5b).

## Зачем

Сегодня модель для задачи выбирается из статического списка предпочтений на класс нагрузки. Роутер выбирает среди уже допущенных кандидатов по свидетельствам и по остатку мощности подписок и записывает, почему. Он никогда ничего не допускает, ничего не запускает и никогда не переключает учётные записи или выход в сеть.

## Как это сочетается с выбором агентов

Резолвер выбора агентов (`skill-project-management/.specs/drafts/agent-selection.md` §7) — это CandidateResolver роутера.

- Его жёсткие фильтры отвечают на вопросы «разрешено», «совместимо» и «доступно». На его шаге ранжирования работает стратегия роутинга.
- Потребности ролей из playbook'ов — это признаки требований роутера. Предпочтения ролей — априорные оценки. Жёсткие требования никогда не нарушаются.
- Свидетельства хранятся по роли или классу требований и по отпечатку исполнения.

### Общие контракты, замороженные до параллельных линий

W0 вливает их до старта W1 и W2, чтобы ни одной линии не пришлось гадать или ждать:

1. **Канонический JSON и дайджест:** правила из `model-routing.md` §5 в виде `pkg/canonical` с закоммиченными тестовыми векторами. Это дайджестная часть приложения A0; граничная часть task-board — это W4.
2. **Проекция использования:** члены использования `CandidateSnapshot` из `headroom.md` §3.1, включая `as_of`, версионированную карту областей действия и счётчики in-flight, в виде Go-типов в `pkg/routing`. W1 читает только это; W3 производит только запись из `headroom.md` §3; отображение одного в другое — это W4 и W5.
3. **Каркасы DTO из R3 и R8** в `pkg/routing`: `TaskEnvelope`, `ExecutionCandidate`, `CandidateSnapshot`, `EvaluationSnapshot`, `RoutingPolicy` с её параметрами запаса и `RoutingDecision`.
4. **Шов оценки:** тип `Estimate` (на кандидата: пригодность, покрытие, идентификаторы записей, давших вклад, версия оценщика) и интерфейс `FitnessEstimator`, оба в `pkg/routing`. Стратегиям W1 оценщик не нужен (`config-order` и `headroom-aware` поверх него). W2 реализует оценщик поверх представления пригодности для ролей на этапе B, после слияния обеих линий.
5. **Ссылки на свидетельства:** `EvaluationSnapshot` называет свой снимок свидетельств по дайджесту, а его оценки ссылаются на идентификаторы записей (`evidence-format.md` §2.0).

Изменение замороженного контракта после W0 — это отдельный проверенный PR, объявленный другим линиям до слияния.

### Владение пакетами внутри curator-model-router

W1 и W2 идут одновременно и не сталкиваются, потому что у каждого свои пакеты:

| Пакет или файл | Владелец |
| --- | --- |
| `pkg/canonical` | W0 |
| `pkg/routing`: контрактные типы | W0, затем меняется только как замороженный контракт |
| `pkg/routing`: стратегии, записи решений, `explain`, `replay` | W1 |
| `pkg/evidence` | W2 |
| `cmd/cmr` | делится по файлам подкоманд |

W1 никогда не импортирует `pkg/evidence`, а W2 никогда не импортирует стратегии.
