## 0. Цель

Оркестратор передаёт описание работы и её ограничения. Роутер выбирает конфигурацию запуска среди **уже допущенных** кандидатов, записывает, почему выбрал именно её, и передаёт результат существующему механизму запуска. Это не прокси перед API модели, не планировщик и не ещё один агент внутри запуска: это отдельный шаг подготовки запуска, который можно проверить.

Единица выбора — **привязка среды выполнения + модель + уровень рассуждений** (LP-D1) вместе с профилем контекста Curator (LP-D4), профилем движка для локальных моделей (LP-D7), а позже и AgentOffer из пула. Решение относится к одному запуску или одной попытке; переключение модели на каждый запрос внутри агентского цикла вне области этой работы. Первый релиз работает с сегодняшними локальными кандидатами; удалённый пул позже расширит набор, но не является предусловием. Умному выбору не нужен вызов LLM: сопоставление требований задачи с замерами уже даёт полезный выбор, а Jev или структурированная LLM — необязательные сменные оценщики.

## 2. Решения

### R1 Архитектурное место: библиотека с адаптерами вызывающих

Go-модуль с рабочим именем **`curator-model-router`** (собственный репозиторий с 24.09.2026; никогда не сетевой сервис). Он не импортирует ни task-board, ни пути исполнения модуля, ни хранилище ax и не создаёт процессов; вызывающие переводят свои структуры в независимые DTO. Общий резолвер не означает одну глобальную политику: task-board сохраняет свои ограничения ролей и проекта, `curator-run` — машинные блокировки и ограничения окружения; роутер ничего из этого не копирует.

```text
Task / work description / role
        │
        ▼
 Caller adapter (task-board | curator-run)
        │
   ┌────┴──────────────────────────┐
   ▼                               ▼
TaskEnvelope             CandidateResolver
                         registry, policy, locks, catalog binding,
                         context profile, availability, engine status
   │                               │
   │                       EligibleCandidates
   └────────────┬──────────────────┘
                ▼
          curator-model-router:  assess → estimate → select
                ▲
          EvidenceSnapshot (benchmarks, own outcomes)
                │
                ▼
          RoutingDecision
                │
                ▼
     existing spawn gate: revalidate → build → launch
```

Кто чем владеет: task-board — задача, роль, ограничения проекта, режим роутинга, запуск и приёмка; agents-management — идентичность и совместимость среды выполнения, модели, уровня рассуждений и движка, граф плагинов, контракты запуска, машинный каталог; `curator-model-router` — свидетельства, требования, пригодность, стратегии, записи решений; `curator-run` — сочетание выбора с учётом задачи с окружением и конвейером запуска; `curator-inference-manager` — профили движков, их состояние и ёмкость (`ensure` вызывает владелец процесса, а не роутер); хост процесса и будущий координатор — настоящий запуск, ресурсы, резервирования, отмена; Curator — доставка закреплённых пакетов и управляемых домашних каталогов, граница учётной записи.

### R2 Четыре вопроса, четыре владельца

| Вопрос | Кто отвечает | Входные данные |
| --- | --- | --- |
| Разрешено? | политика, заявленная оператором | потолки и допущенные пары; `bound_on_this_machine` (непривязанная среда выполнения исключается до подсчёта оценок, и это не то же, что `no_eligible_candidates`); `spawn.schedule` проекта и `windows` каталога; допуск по тарификации; политика данных проекта |
| Технически совместимо? | реестр модуля + каталог | инструменты, словарь уровней рассуждений, окно контекста, транспорт, профиль движка, режим исполнения |
| Подходит для работы? | оценщик пригодности роутера | требования ↔ замеры или явно помеченные оценки |
| Доступно сейчас? | блок доступности предварительной проверки (LP-D9) | инвентарь и авторизация, квота, реактивные лимиты, состояние движка в виде двух фактов (`ready`: serving или lingering; `ensurable`: профиль и веса на месте, не в карантине, арбитраж хоста пропустил бы `ensure`) и аренды, всё с ключом `(runtime, managed home)` |

Оценщик пригодности отвечает только на третий вопрос. Положительная оценка никогда не перекрывает остальные три. Прогноз — не принуждение: «это уложится в бюджет» ничего не ограничивает, лимиты применяет владелец исполнения. Если подходящих кандидатов нет, ответ `no_eligible_candidates` возвращается **до** запуска любого платного оценщика. Холодный, но запускаемый движок оставляет своего кандидата пригодным и добавляет стоимость старта (R6); исключает его только «не ensurable». Иначе остановленный движок никогда не был бы выбран, а значит, и запущен (LP-D9, поправка от 2026-09-22).

### R3 Модель данных

Шесть объектов: `TaskEnvelope` (делегируемая работа: описание, содержательная ревизия, роль, критерии, контекст, инструменты; конкретная задача, а не весь эпик и не разговор оркестратора), `ExecutionCandidate`, `CandidateSnapshot` (допущенный набор и то, как он получен), `EvaluationSnapshot` (замеры, рубрика, оценки, прогнозы, версии оценщиков), `RoutingPolicy` (что можно выбирать, как сравнивать, что делать при нехватке данных), `RoutingDecision`.

`ExecutionCandidate` — это конфигурация, которую действительно можно запустить:

```text
runtime binding id + model + effort            (LP-D1)
Curator context profile {name, lock_sha256}    (LP-D4)
transport and provider id from runtimes.toml    (LP-D3)
engine profile from engines.toml (local models) (LP-D7)
network profile, resolved by the caller       (NP-N4 precedence)
tool profile / execution mode
AgentOffer, compatible EnvironmentBinding       (later, pool)
```

Отпечаток исполнения для сопоставления свидетельств: идентичность вендора и модели, версия агентской среды, уровень рассуждений, профиль движка (вид движка, дайджест весов, квантование, `kv_context_tokens`, `prefill_chunk_tokens`; позже тип KV-кэша, этап K4), профиль окружения и инструментов, профиль исполнения. Для облачного алиаса точная внутренняя версия записывается как неизвестная и никогда не подделывается под закреплённую. Приватные члены (адреса с учётными данными, пути, PID) никогда не попадают в отпечаток: он строится из публичного `RuntimeProvenance` (LP-D11). Дайджест работы не меняется на каждом переходе `ready → running`: содержимое и критерии — это одно, текущая исполнимость — дело рабочего процесса.

### R4 Свидетельства

Источники по порядку: адаптер над существующими наблюдениями Bug Hunt, импорт JSON для собственных прогонов оценки и (после появления обратной связи) результаты обычных запусков. Единица хранения:

```text
Observation
    execution_fingerprint
    benchmark / dataset / split
    evaluation_protocol_digest
    metric / unit / direction
    value / sample_count / uncertainty
    evidence_kind      measured | interpolated | transferred
    grading_method     tests | exact-match | llm-judge | human
    provenance / raw_artifact_ref
    observed_at
```

`evidence_kind` и `grading_method` независимы: результат LLM-судьи может быть настоящим наблюдением, не становясь результатом тестового оракула. Семантика: нет замера — значит *неизвестно*, а не ноль; нет цены — *неизвестно*, а не бесплатно; неизвестная модель в файле — *неразрешённое наблюдение*, а не регистрация среды выполнения. Рейтинги никогда не усредняются: оценщик пригодности явно указывает, как требования отображаются на замеры, как они нормализуются и где применимы; перепечатки одного результата — не независимые подтверждения. Замер на одном уровне рассуждений никогда не выдаётся за замер на другом, а оценка, выведенная для другого уровня, существует только как `evidence_kind = transferred` со своей неопределённостью и явно указанным правилом переноса. Импорт создаёт новый снимок и никогда не переписывает глобальный `Rank.Score` модуля.

### R5 Контракты оценщиков

Вместо `Evaluator(any) → float` пять узких интерфейсов: `EvidenceSource` (импорт наблюдений), `TaskAssessor` (работа → требования и признаки), `FitnessEstimator` (требования + кандидаты + свидетельства → пригодность), `SelectionStrategy` (замороженные оценки + предпочтения → выбор или отказ от выбора), `OutcomeEvaluator` (результат и проверки → наблюдение о качестве, но не право принять работу). Прогон бенчмарка — отдельная необязательная возможность, которая никогда не прячется внутри импорта.

Первый `TaskAssessor` детерминирован: существующее выведение класса нагрузки плюс явные метаданные задачи (роль, язык, тип изменения, ожидаемый контекст, инструменты). Следующим идёт оценщик по рубрике поверх общего `JudgmentBackend` (Jev с типизированными Choice/Score/Noul или структурированная LLM), выбранного **явно**, чтобы роутер никогда не выбирал модель, которая выбирает модель роутера. Уверенность классификатора — не вероятность успеха агента: уверенность, покрытие свидетельствами и эмпирическая калибровка — разные поля. Логические стадии — это не пять платных вызовов: требования определяются одним ограниченным вызовом, пригодность считается локально.

### R6 Выбор

Относительная полезность, а не заявленная вероятность успеха. Порядок: пригоден и совместим → достаточное качество и покрытие свидетельствами → предпочтение по стоимости, задержке и качеству → стабильное разрешение ничьей → выбор или отказ от выбора; так низкая цена никогда не компенсирует сколь угодно плохое качество. Стратегии: `config-order` (сегодняшнее поведение как база), `quality-first`, `cost-with-quality-floor` (порог ссылается на версию рубрики или оценщика; `0.9` без шкалы ничего не значит). `calibrated_success_probability` — более поздний тип, который валидируется отдельно. Стоимость — не одно число: оценка счёта за API, расход квоты (providerquota на управляемый домашний каталог), задержка, занятость локального движка из `curator-inference-manager status`, стоимость старта холодного, но запускаемого движка; класс `billing` в каталоге (`local | subscription | metered`, LP-D9) определяет, что из этого применяется. **Селектор — чистая функция** над замороженными входными данными: без сети, файлов, часов и вызовов моделей, поэтому воспроизведение повторяет решение, даже если оценщик был недетерминированным.

### R7 Режимы, значения по умолчанию, ручной выбор

| Режим | Поведение |
| --- | --- |
| `off` (прежнее поведение) | всё как сегодня |
| `shadow` | решение записывается, фактический выбор не меняется |
| `recommend` | вызывающий получает рекомендацию и выбирает явно |
| `select` | вызывающий разрешает роутеру заполнить допустимые поля |

Блокировки и явные значения никогда не заменяются: если заданы `--agent` и `--model`, роутер может выбрать только уровень рассуждений, и только если это разрешено. `select` требует явной маски свободных полей, где названы члены кандидата, которым разрешено отличаться: среда выполнения, модель и уровень рассуждений по запросу, а зависимые настройки (сетевой профиль и профиль контекста) — только если их явно освободили. CandidateResolver сначала разрешает зависимые настройки каждого кандидата (значение по умолчанию привязки → проекта → оператора, NP-N4; профиль контекста по LP-D4). Каждое явно запрошенное значение он фиксирует для всех кандидатов и до подсчёта оценок исключает кандидата, у которого разрешённая зависимая настройка отличается от зафиксированного или неосвобождённого значения, с кодом `candidate_dependent_setting_mismatch`. Роутер выбирает среди целых вариантов и не правит ни одного члена; владелец процесса заново разрешает и применяет выбранный вариант. Поэтому выбор привязки, у которой значения по умолчанию подразумевают другой выход в сеть, — это разрешённый выбор целого варианта, когда маска освобождает сетевой член, а не переключение маршрута роутером (NP-N13). Мягкие значения по умолчанию для ролей становятся базой, а не окончательным ответом. `abstain`, `no_eligible_candidates`, тайм-аут и некорректный ответ — разные исходы. По умолчанию `select` ничего не запускает, если решения нет; явный переход на базовый вариант разрешён только по названным причинам, записывается как `origin: baseline_after_abstain` и никогда не перекрывает обязательный порог свидетельств.

### R8 RoutingDecision и срок действия

```text
RoutingDecision
    decision_id / schema_version
    task_envelope_digest / role_context_digest
    candidate_snapshot_digest / evaluation_snapshot_digest / routing_policy_digest
    assessor / estimator / selector versions
    selected_candidate {runtime, model, effort, context_profile, network_profile?, engine_profile?}
    alternatives, reason_codes, evidence_refs
    selection_origin, applicability_scope, prepared_at / expires_at
```

Объяснение для человека строится из структурированных причин; свободный текст оценщика никогда не решает, какие среда выполнения, модель и уровень рассуждений будут выбраны. Дайджест фиксирует содержимое, а не авторство: для MVP достаточно доверенного локального хранилища, между машинами нужна аутентифицированная доставка или подпись. `decision_id` адресуется содержимым, либо ссылка несёт дайджест решения рядом с идентификатором. В обоих случаях ссылка из подписанного назначения указывает на одну неизменяемую запись и связывает её с конкретными параметрами исполнения, которые несёт назначение. Изменения бывают двух видов: **содержательные** (задача, роль, политика, идентичность модели, профиль инструментов, блокировка профиля контекста, ссылка на сетевой профиль) делают решение устаревшим; **операционные** (heartbeat, квота, слот) требуют свежей проверки доступности, а не побайтового совпадения изменчивого снимка. Если кандидат стал недоступен, возвращается `selected_candidate_unavailable`; повторный выбор — новая операция, которая переиспользует сохранённые оценки для неизменившихся конфигураций. Поэтому проверка сравнивает по членам: содержательные члены — с сохранённым решением по дайджесту, операционные — через свежее чтение доступности; один дайджест на всю предварительную проверку никогда не сравнивается. Роутер ничего не резервирует и не ведёт второго счётчика квот.

### R9 Интеграция с task-board

- Первый рефакторинг: вынести один `CandidateResolver` из проекции нагрузки и сделать `config-order` базовой стратегией; запрос, подготовка роутинга и проверка запуска идут по одному пути для потолков, расписаний, лимитов провайдеров, привязки каталога и доступности. Машинная половина (каталог, `bound_on_this_machine` в предварительной проверке, разрешение зависимых настроек) зависит от фазы 1 LP и составляет этап A1; этап A0 выносит резолвер и воспроизводит `config-order` без неё.
- Подготовка — явная операция; `project_config` никогда не превращается в скрытый вызов Jev. CLI (*предложено*): `task-board routing prepare TASK_ID --role R --policy P --json`, `routing explain DECISION_ID`, `routing replay DECISION_ID`. `prepare` не создаёт worktree и не запускает субагента; с внешним оценщиком это явно платная операция.
- Оркестратор получает выбранного кандидата и `decision_id`, а затем передаёт явные параметры обычному запуску: `--agent <runtime-id> --model <id> --reasoning-effort <e> --context-profile <name>` и, если решение его несёт, `--network-profile <ref>` (словарь LP-D12; без `--profile`), плюс `--routing-decision <id>` (*предложено*), который привязывает решение так же, как сегодня `--recommendation-snapshot-digest` привязывает рекомендацию. Удобный `spawn --route` позже может собирать те же шаги, но не должен становиться вторым роутером.
- Две фазы проверки: ранняя (формат, авторство, привязка политики, выбранный кандидат) до любого побочного эффекта и поздняя — после обычного чтения задачи (содержательная ревизия и контекст). Несовпадение ведёт к отказу; внутри запуска нет вызовов LLM. Существующий порядок, захваты и уборка сохраняются.
- Доказательство фактической конфигурации: манифест запуска (`RuntimeProvenance` + блокировка профиля Curator, LP-D11) сравнивается с решением. Для codex переопределения `-c model_provider`, а для claude собственные литералы окружения входят в план модуля и поэтому применяются по построению; нативные аргументы, переопределения `-c` после `--` или автоматический режим агентской среды не должны молча менять модель после проверки. Адаптер, который не может подтвердить фактическую конфигурацию, может поддерживать `recommend`, но не должен заявлять строгий `select`.

### R10 Лаунчер Curator

Отдельный режим с учётом задачи: описание работы или ссылка на подготовленное решение плюс профиль выбора. Сначала разрешаются окружение, блокировки и явные значения; роутер получает оставшийся набор; затем идут обычный `BuildLaunchWithEnvironment` и отдельная проверка доступности. task-board не запускает через `curator-run` (LP-D5); оба потребителя используют библиотеку через собственные адаптеры.

### R11 Сетевые профили, движки, пул

`curator-model-router` решает, что запускать; `curator-network-profiles` решает, какой маршрут разрешён (NP-N13). Роутер может учитывать совместимость с обязательным сетевым профилем как ограничение; он никогда не переключает VPN, учётные данные или домены квот; сбой сети — не свидетельство о качестве модели. Движки: роутер может учитывать ёмкость `engine.profile` как совместимость и стоимость; `curator-inference-manager ensure` — действие предварительной проверки владельца процесса, а не роутера. Пул (позже): `ExecutionOption = ExecutionCandidate + AgentOffer + compatible EnvironmentBinding`; машина для инференса и машина для инструментов разные, поэтому требование Xcode проверяется на среде исполнения, а не на рабочем агенте; координатор подтверждает размещение и резервирует; правила независимости ревьюера применяются до подсчёта оценок.

### R12 Повтор и обратная связь

Повтор по лимитам провайдера сохраняет свою замороженную политику; в первой интеграции решение роутинга явно покрывает первую попытку, а последующие попытки записывают свою фактическую конфигурацию и ссылку на решение. Жёсткие ограничения соблюдаются всегда. Строгая политика, несовместимая со старым повтором, отказывает или запрещает смену кандидата, а новый снимок, оценщик или цель никогда не подмешиваются между попытками молча. Эскалация по качеству после плохого результата — решение рабочего процесса, а не повтор по лимитам провайдера. Обратная связь берётся из результата, а не из самоотчёта агента: `decision_id`, `run_id/attempt_id`, `actual_execution_fingerprint` (позже включая профиль движка и тип KV-кэша), `kv_outcome` `warm|restored|cold` (`warm`: переиспользован удержанный живой слот; `restored`: восстановлен снимок; `cold`: полный prefill) или `unknown` с кодом причины, если его нельзя измерить; исход всегда измеряется по usage атрибутированного главного запроса запуска, а не по последнему увиденному запросу (LP-D10; Q9 трека KV, 2026-10-01), `artifact_revision`, проверки, ревью и приёмка, фактические расход, задержка и ресурсы, `failure_class` (ошибка модели, сеть, авторизация или лимит, окружение, `engine_ensure_failed`, отмена и незавершённая оценка различаются; неизвестное остаётся неизвестным). `OutcomeEvaluator` формирует наблюдение, а приёмка остаётся за рабочим процессом. Новые исходы попадают в следующий снимок и никогда не меняют активную стратегию после каждой задачи; обученные оценщики и артефакты калибровки выходят отдельными версиями после ревью.

### R13 Стоимость, приватность, расширения

Роутер должен стоить дешевле ценности своего выбора: политика ограничивает размер проекции задачи, внешние вызовы, время и стоимость; мелкие задачи решаются правилами и кэшированными оценками. Кэши разделены: `TaskAssessment` (задача + рубрика + бэкенд), `CandidateEstimates` (оценка + кандидаты + свидетельства), `Selection` (прогнозы + предпочтения); текущая доступность никогда не кэшируется как постоянное разрешение; кэши соблюдают границы проектов и политику данных. Первый путь для плагинов — доверенные Go-компоненты в корне композиции; внешние расширения позже, через ограниченный версионированный RPC по stdio. Реестр проверяет граф зависимостей, а не безопасность плагинов: права, секреты и сеть выдаёт хост, а не манифест оценщика.

## 3. Этапы и приёмка

| Этап | Что даёт | Ценность |
| --- | --- | --- |
| A0. База и контракты | общий резолвер, `ConfigOrderStrategy`, DTO, `RoutingDecision`, регрессионные тесты (совпадение с прежним поведением), приложение с контрактом из §5; без машинной половины | сегодняшний выбор воспроизводится и объясняется через один путь |
| A1. Машинная половина | каталог, `bound_on_this_machine`, разрешение зависимых настроек и код причины несовпадения | кандидаты — настоящие привязки сред выполнения этой машины |
| B. Рекомендации по свидетельствам | адаптер Bug Hunt, импорт JSON, снимки, оценщик по правилам, детерминированный оценщик пригодности | рекомендации, зависящие от работы и замеров, без обязательной LLM |
| C. Смысловая оценка | рубрика, бэкенды Jev и LLM, бюджеты, приватность, теневой режим | более богатая оценка задачи без изменения фактического выбора |
| D. Выбор по согласию при запуске | двухфазный шлюз, происхождение, адаптеры вызывающих, обратная связь по фактической попытке | оркестратор действительно делегирует выбор |
| E. Эмпирическое улучшение | наборы для оценки, калибровка, контролируемые эксперименты; позже адаптер пула | улучшение доказано на собственных задачах |

C не является зависимостью для D. Первые боевые профили включаются для ограниченных классов задач и кандидатов. Зависимости от LP: A0 начинается сейчас; A1 — после фазы 1 LP (каталог); этап B идёт рядом с фазой 3 LP и берёт её блок доступности как единственный источник «доступно сейчас», включая факты движков `ready`/`ensurable`.

Проверки готовности:
- роутинг `off` сохраняет значения по умолчанию, допуск, допущенные нерекомендованные варианты и повтор;
- новая оценка никогда не допускает запрещённую модель и никогда не заменяет блокировки или явные значения;
- неизвестное, интерполяция и перенос никогда не выдаются за прямой замер;
- сохранённые входные данные воспроизводят выбор без сети и без модели;
- другая задача, политика или конфигурация отклоняется, а обычный heartbeat не создаёт ложного устаревания;
- запрос никогда не вызывает оценщика, подготовка никогда не запускает рабочего агента, селектор никогда не резервирует;
- выбранная конфигурация действительно применяется, включая нативные переопределения;
- отказ от выбора, тайм-аут, некорректный ответ и отсутствие кандидатов различаются, а переход на базовый вариант явный;
- обратная связь привязана к фактической попытке и проверенной ревизии;
- новый источник или оценщик не меняет ни запуск, ни ядро реестра.

Теневой режим показывает поведение, а не превосходство: ценность измеряется на воспроизведении, на отложенных задачах или в ограниченных экспериментах с равными критериями и бюджетом, по качеству принятого результата, полной стоимости до приёмки с учётом роутинга и повторов, времени, покрытию и доле отказов от выбора. Обучение только на истории выбранных моделей — смещённая выборка.

## 4. Правила и не-цели

- Один граф плагинов, один путь допуска, отдельная оценка, чистый селектор, записанное решение, существующий запуск.
- Никогда процесс из роутера; никогда резервирование; никогда скрытый вызов LLM в локальном запросе; никогда оценка, расширяющая допуск; никогда свободный текст как основание для выбора среды выполнения, модели и уровня рассуждений.
- Словарь: привязка среды выполнения, а не «строка модели»; `--agent`/`--runtime`, `--context-profile`, `--network-profile`; никогда `--profile`.

## 5. Приложение с контрактом (результат этапа A0)

Формы объектов даны в R3 и R8; точные правила сравнения и воспроизведения пишутся вместе с кодом как короткое приложение с тестовыми векторами. Решено сейчас:

| Область | Правило |
| --- | --- |
| Дайджест | канонический JSON с отсортированными ключами и явной версией схемы, SHA-256 по этим байтам; значения по умолчанию материализуются до хеширования; коллекции упорядочены по объявленному ключу, а не по порядку вставки или обхода map |
| Неизвестное | отсутствующее поле означает «неизвестно»; каноническая форма не несёт `null`; ноль — это замеренное значение; обязательное поле без значения несёт явный маркер `unknown` |
| Воспроизведение | три снимка, политика и версии оценщиков и селектора воспроизводят решение без доступа к сети, файлам, часам и моделям |
| Разрешение ничьей | стабильный порядок сравнения, затем лексический порядок идентификаторов кандидатов; никогда обход map |
| Проверка запуска | содержательные члены (задача, роль, политика, идентичность модели, профиль инструментов, блокировка профиля контекста, ссылка на сетевой профиль) сравниваются с сохранённым решением; операционные члены (heartbeat, квота, слот, готовность движка, дайджест сетевого профиля) — через свежее чтение доступности |

## 6. Закрытые решения и оставшийся выбор

Закрыто этим документом: роутер — библиотека с адаптерами вызывающих; кандидаты — привязки сред выполнения с членами отпечатка из LP; разделение на четыре вопроса и их владельцы; чистый селектор; четыре режима с маской свободных полей; форма документа решения; двухфазная проверка в task-board; зависимость машинной половины от фазы 1 LP. Добавлено 2026-09-22 после независимого ревью: зависимые настройки (сетевой профиль, профиль контекста) разрешает вызывающий и фиксирует их, если маска их не освобождает, поэтому роутер никогда не переключает маршрут; доступность движка — два факта, `ready` и `ensurable`, и холодный, но запускаемый движок остаётся пригодным со стоимостью старта; свидетельства с другого уровня рассуждений существуют только как `transferred`; проверка сравнивает по членам; этап A разделён на A0 (сейчас) и A1 (после фазы 1 LP); приложение с контрактом из §5 — результат A0. После второго ревью: `decision_id` адресуется содержимым или передаётся вместе со своим дайджестом, так что подписанное назначение связывает одно неизменяемое решение с параметрами исполнения, которые оно несёт.

Добавлено 2026-10-01 из трека KV-кэша (решение оператора; wiki `research/kv-cache-orchestration/ARCHITECTURE.md`, Q9 согласован с владельцем LP):

- Исход KV-кэша в R12: `warm|restored|cold` или `unknown` с кодом причины, измеренный по usage атрибутированного главного запроса. LP-D10 со стороны LP меняется на ту же формулировку.
- Состояние KV никогда не допускает и не отклоняет кандидата, по принципу LP-D9 и R2: отсутствующее или неудачное состояние KV — это зафиксированный холодный prefill. Его термы в роутере — этап K4 в `spec/track.md`, который ждёт телеметрии K2a.
