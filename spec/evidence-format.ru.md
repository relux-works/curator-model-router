# Формат свидетельств: спецификация

Статус: **ЧЕРНОВИК**, 2026-10-01. Он расширяет R4 из `spec/model-routing.md` и реализует требование 1 решений оператора от 2026-09-30 (решение оператора). При расхождении этот файл задаёт форму свидетельств, а `model-routing.md` — то, как их использует роутер.

Размещение следует решению D1 из этого решения:

- Формат, хранилище, импортёры и производные представления живут в этом репозитории.
- agents-management держит факты реестра, на которые они ссылаются: идентификаторы моделей, построчные бенч-данные в `vendorplugin/bench.go` и планируемое поле `ExternalIDs` в строке реестра.

Это заменяет размещение, предложенное в дизайне хранилища свидетельств в task-board, где хранилище свидетельств лежало в пакете модуля рядом с `providerlimits`.

---

## 0. Цель

Любой бенчмарк, прогон оценки, исход ревью или суждение оператора приводится к одному внутреннему формату, прежде чем его прочитает роутер.

- Оценщик, представление пригодности для ролей и `explain` читают только этот формат и ничего больше.
- Импортёры — единственный код, который знает исходную форму источника.
- Поэтому новому источнику нужен только новый импортёр и ничего больше.

Запись явно называет пять вещей и никогда не оставляет их подразумеваемыми:

1. какой бенчмарк, какая версия и какой протокол оценки;
2. за какие категории задач говорит значение;
3. точную модель и уровень рассуждений, на которых оно измерено;
4. метрику с единицей, направлением, объёмом выборки, неопределённостью, видом свидетельства, методом оценки и происхождением;
5. для внутреннего суждения, а не измерения: кто утверждает, на каком основании, насколько уверен и до каких пор.

## 1. Документы

Свидетельства движутся в документах двух видов. Оба — канонический JSON: правила дайджеста — из `model-routing.md` §5.

| Документ | Содержимое | Изменяемость |
| --- | --- | --- |
| `evidence-import` | один импорт из одного источника: заголовок, `benchmarks[]`, `observations[]`, `notes[]`, `retractions[]` | неизменяем после сохранения; исправление — это новый импорт |
| `evidence-snapshot` | набор действующих дайджестов импортов, версия таксономии и ссылка на реестр, по которой разрешаются идентификаторы моделей | неизменяем; новый импорт даёт новый снимок |

**Заголовок импорта:**

- `schema_version`;
- `source`: стабильный слаг, например `bug-hunt`, `internal-evals`, `run-outcomes` или `operator-notes`;
- `importer {name, version}`;
- `imported_at`;
- `measured_by`: `vendor`, `third_party` или `internal`.

`measured_by` фиксирует независимость. Число от вендора — всё равно измерение по протоколу вендора, но не независимое подтверждение.

**Идентичность снимка.** `EvaluationSnapshot` (R3) называет ровно один снимок свидетельств по дайджесту. Производные представления (§4) вычисляются для каждого снимка и никогда не импортируются.

## 2. Записи

### 2.0 Идентичность записей, замена и отзыв

**Стабильные адреса:**

- бенчмарк — это `{id}@{version}`;
- наблюдение — это `obs:` плюс SHA-256 его канонической формы без поля `id`;
- заметка — это `note:` плюс SHA-256 её канонической формы без поля `id`;
- отзыв — это `ret:` плюс SHA-256 его канонической формы без поля `id`.

Вклады, `supersedes`, исправления, `evidence_refs` и `explain` ссылаются на эти адреса.

**Замена и отзыв — только добавлением:**

- Наблюдение или заметка может нести `supersedes: [ids]`. Её импорт и есть исправление; заменённые записи остаются в своих импортах.
- Запись `retraction {target, reason, author, at}` отзывает цель без замены. Сам отзыв отозвать нельзя: чтобы вернуть отозванную запись, импортируйте новую запись.

**Активное множество.** Возьмите все записи импортов снимка.

1. Отозванная запись изъята: она не активна и ничего не заменяет. Её рёбра `supersedes` отбрасываются.
2. Оставшиеся рёбра образуют граф замен. Импорт, замыкающий цикл, отклоняется.
3. Запись **активна**, когда она не отозвана и ни один путь из одного или более оставшихся рёбер не ведёт к ней.

**Следствия.**

- В цепочке C → B → A активна только C.
- Отзыв C оживляет B, а A остаётся подавленной через B.
- Отзыв B оставляет C активной и оживляет A, потому что C называла только B. Замена, которая должна заменить всю линию, называет каждую запись, которую заменяет.

**Статус рассчитывается, а не хранится.** Статус записи (`active`, `superseded` или `retracted`) вычисляется по этому правилу и показывается в `explain` и `cmr evidence show`. Никакое импортированное поле не может ему противоречить.

**Конфликты фиксируются, а не угадываются.** Когда две активные записи заменяют одну цель, обе остаются активными. Снимок сообщает `evidence_conflict`, а расчёт читает обе. Это детерминировано, потому что активное множество не зависит от порядка импортов.

### 2.1 Бенчмарк

```text
benchmark
    id                  stable slug: "bug-hunt-bench", "swe-bench-verified", "internal-review-set"
    version             exact version or dataset revision
    publisher           who runs it
    dataset / split     optional
    protocol_digest     digest of the evaluation protocol (scaffold, prompts, limits) when known
    categories[]        task categories it speaks for (§3), each with a one-line coverage note
    metrics[]           {name, unit, direction: higher_better | lower_better, scale?, description}
    grading_method      tests | exact-match | llm-judge | human | mixed
    citation            optional URL or reference
```

**Версии.** Бенчмарк с изменившейся версией или протоколом — это новый `{id, version}`. Наблюдения разных версий никогда не объединяются, если объявленное отображение не говорит, что они совместимы.

### 2.2 Наблюдение

Одно измеренное или выведенное значение.

```text
observation
    benchmark_ref               {id, version}
    subject
        model_id                registry id (agents-management), e.g. "gpt-6.1-sol"
        runtime                 runtime id when the source fixes it, else absent (= unknown)
        harness_version         when known
        effort                  the effort token as launched, verbatim; "none" for a model that takes none
        engine_profile          local models only (LP-D7 members)
        tool_profile / execution_profile   when known
    subject_resolution          resolved | unresolved
    categories[]                the subset of the benchmark's categories this value speaks for
    facets                      {languages[], platforms[]}  optional
    metric                      a name from the benchmark's metrics
    value
    sample_count                integer, or absent (= unknown)
    uncertainty                 {kind: stderr | ci95 | range, value}, or absent
    evidence_kind               measured | interpolated | transferred
    transfer                    required when transferred: {from: {model_id?, effort?}, rule_id, rule_version}
    supersedes                  optional: [ids] this observation replaces (§2.0)
    grading_method              tests | exact-match | llm-judge | human
    cost                        optional per sample: tokens_in, tokens_out, usd, wall_s; each absent = unknown
    provenance                  {source, retrieved_at, raw_artifact_ref, origin_ref}
    observed_at                 when the measurement was taken, not when it was imported
```

**Уровень рассуждений точен.**

- `effort` — это токен, с которым запустили харнесс, дословно: сегодня `low`, `medium`, `high`, `xhigh` или `max`, либо `none`. Он проверяется по зафиксированному словарю уровней рассуждений реестра для этой модели (agents-management), а не по списку из этого файла. Токен, которого словарь не знает, сохраняется, помечается `effort_unrecognised` и никогда не сопоставляется.
- Источник, который не называет уровень, даёт отсутствующий уровень, то есть неизвестный. Значение по умолчанию от вендора никогда не предполагается.
- Наблюдение с неизвестным уровнем никогда не сопоставляется с уровнем кандидата.
- Значение, перенесённое на другой уровень или на другую модель, существует только как `evidence_kind = transferred`. Оно называет своё правило переноса и его версию и несёт собственную неопределённость (R4).

**Идентичность модели.**

- `model_id` — это идентификатор реестра agents-management.
- Внешнее имя источника отображается через `ExternalIDs` строки реестра, когда это поле есть, либо через таблицу отображения импортёра, которая несёт собственную версию.
- Неотображённое имя сохраняется с `subject_resolution = unresolved` и попадает в отчёт снимка `unresolved`. Оно никогда не регистрируется, никогда не сопоставляется и никогда не отбрасывается.

**Независимость.** `provenance.origin_ref` называет исходную публикацию или прогон. Перепечатки одного результата делят один `origin_ref` и считаются один раз (R4).

### 2.3 Заметка: внутреннее наблюдение о модели

Курируемое суждение, например «хорош для ревью», «хорош для реализации на Go» или «слаб в работе под Windows».

```text
note
    subject             {model_id, runtime?, efforts[]?, harness_version_range?}
    claim
        polarity        strength | weakness | caution
        statement       one short sentence
        categories[]    task categories it concerns (§3)
        facets          {languages[], platforms[], roles[]}  optional
    basis               review-outcomes | run-outcomes | operator-judgement | incident | benchmark-reading
    evidence_refs[]     {kind: run | review | pull-request | board-element | observation | document, ref}
    confidence          low | medium | high
    author              {kind: human | agent, id}
    created_at
    review_by           the date after which the note is stale unless re-confirmed
    supersedes          optional: [ids] this note replaces (§2.0)
```

**Заметки — априорные оценки, а не измерения.**

- Заметка никогда не становится наблюдением и никогда не несёт числа, похожего на метрику.
- Оценщик взвешивает заметку по `confidence` и `basis` с весами, объявленными в версии расчёта (§4).
- `explain` показывает заметки отдельно от измерений.
- После `review_by` заметка устаревает. Она показывается с возрастом, а её вес равен нулю, если политика не говорит иначе.

**Заметки — никогда не политика.** Заметка никогда не допускает и не убирает кандидата. «Никогда не использовать модель X для задачи Y» — это политика оператора, и ей место в файлах оператора (`models.toml`, потолки ролей), а не в свидетельствах.

**Примеры** в форме выше, из записанной практики оператора:

| Субъект | Утверждение | Основание |
| --- | --- | --- |
| `claude-sonnet-5-5` / `high` | strength: надёжный исполнитель для реализации и рутинных ревью; категории `code.implement`, `review.code` | operator-judgement |
| `gpt-6-astra` / `high` | strength: подходит для ответственных ревью; категории `review.code`; роли `reviewer` | operator-judgement |
| `gpt-6-luna` / `max` | weakness: работа под Windows неоднократно не проходит ревью; платформы `windows` | review-outcomes |

## 3. Категории задач

Версионированный контролируемый словарь, таксономия **v1**:

| Категория | Охватывает |
| --- | --- |
| `code.implement` | новый функционал, код фич |
| `code.fix` | исправление по воспроизведению |
| `code.refactor` | изменение с сохранением поведения |
| `code.test` | написание или починка тестов |
| `review.code` | ревью изменения кода |
| `review.spec` | ревью спецификации или дизайна |
| `docs.write` | документация и справочные страницы |
| `research` | исследование по источникам, письменные выводы |
| `planning` | декомпозиция, оценки, планы |
| `orchestration` | координация дочерних агентов на длинном горизонте |
| `tool-use` | агентская работа в терминале и с инструментами |
| `ops` | CI, инфраструктура, релизные рутинные задачи |
| `routine` | механические правки, форматирование, перевод |

**Фасеты** уточняют категорию, не умножая словарь:

- `language`: `go`, `swift`, `python`, `typescript` и так далее;
- `platform`: `macos`, `ios`, `linux`, `windows`, `android`;
- `context_size`: `small`, `medium`, `large`;
- `horizon`: `short`, `long`.

**Правила.**

- Новая категория требует новой версии таксономии.
- Импорт, использующий категорию, неизвестную таксономии снимка, сохраняется. Категория фиксируется в отчёте, никогда не отбрасывается и никогда молча не отображается.
- Отображение классов нагрузки task-board и потребностей ролей из playbook'ов на категории — это объявленная версионированная таблица. Она входит в расчёт (§4), а не в какой-либо импорт.

## 4. Пригодность для ролей: производное представление

Для каждой роли и кандидата представление говорит, насколько кандидат подходит и почему:

```text
role_suitability
    role            a playbook role alias: orchestrator, developer, reviewer, researcher, ...
    candidate       the public execution fingerprint of R3: {model_id, effort, runtime, harness_version,
                    engine_profile, tool_profile, execution_profile}; members may be unknown
    grade           strong | adequate | weak | unknown
    score           optional, with its scale
    coverage        per required category: measured | interpolated | transferred | notes-only | none,
                    each marked direct or partial (§4, matching)
    contributions[] {ref: an observation or note, direction: + | -, weight}
    derivation      {name, version, digest}
```

**Входы:**

- требования роли: потребности роли из playbook'ов, отображённые на категории и фасеты с весами через объявленную таблицу из §3;
- наблюдения и заметки снимка;
- версия расчёта, которая объявляет нормализацию метрик по бенчмаркам, веса заметок и пороги градаций.

**Сопоставление наблюдения кандидату:**

| Член | Правило |
| --- | --- |
| `model_id`, `effort` | должны быть известны с обеих сторон и равны; неизвестный уровень никогда не сопоставляется (§2.2) |
| любой другой член отпечатка | известны с обеих сторон и равны: совпадение. Известны с обеих сторон и различаются: нет совпадения. Неизвестны с одной стороны или с обеих: совпадение `partial`, чью скидку веса объявляет версия расчёта. |

`coverage` фиксирует совпадения `partial` как таковые, так что замер на другой версии харнесса или другом профиле движка никогда не показывается как прямой.

**Идентичность представления.** Представление зависит не только от снимка, поэтому его идентичность связывает каждый вход:

- дайджест снимка свидетельств;
- дайджест расчёта;
- дайджест требований ролей: потребности ролей и таблица отображения категорий, для каждого проекта;
- дайджест весов и политики;
- `evaluated_at`, замороженное время оценки, которое решает устаревание заметок;
- дайджест набора кандидатов: отсортированные полные отпечатки кандидатов, которых покрывает представление.

Идентификатор представления — это дайджест по этим шести. Ни истечение заметок, ни требования другого проекта не могут молча изменить представление или переиспользовать его.

**Правила.**

- Представление пересчитывается для каждого различного набора входов и никогда не правится вручную.
- Оно хранится под своим идентификатором, со списком входов внутри, так что `explain` и повтор читают одно представление.
- Категория без свидетельств даёт покрытие `none`, а не нулевой балл. `unknown` — самостоятельная градация пригодности.
- Представление советует оценщику (R5). Оно никогда не допускает кандидата и никогда не переупорядочивает между вендорами по `Rank.Score` модуля, который модуль объявляет несравнимым между вендорами.

## 5. Правила из R4 и новые правила

- Отсутствующее поле означает «неизвестно». Ноль — это измеренное значение. Отсутствующая цена неизвестна, а не бесплатна.
- Лидерборды никогда не усредняются. Два бенчмарка объединяются только через объявленное отображение, с указанной нормализацией и применимостью.
- Импорт никогда не меняет ранний импорт. Исправление — это новый импорт, чьи записи называют те, что они заменяют.
- Хранилище никогда не пишет в реестр и никогда не переписывает `Rank.Score` модуля.
- Приватность:
  - сырые артефакты хранятся по ссылке (`raw_artifact_ref`), никогда инлайн;
  - записи не несут секретов, учётных данных, приватных имён хостов или путей и личных контактных данных;
  - `evidence_refs` могут называть приватные идентификаторы, например идентификатор запуска или элемента доски; для роутера они непрозрачны.
- Наблюдения сами по себе не истекают. Политика может фильтровать по `observed_at` или по `harness_version`. Смена харнесса или модели — это другой субъект, никогда не обновление на месте.

## 6. Импортёры

| Источник | Импортёр | Когда |
| --- | --- | --- |
| Строки Bug Hunt в agents-management `vendorplugin/bench.go` | `bughunt`: читает экспортированные бенч-данные модуля для зафиксированной версии модуля; сохраняет `measured` и `interpolated` как их заявляет модуль; импортирует строки стоимости как `cost` | W2 |
| Файл уже в этом формате | `native`: проверяет, каноникализирует, сообщает о неизвестных категориях и неразрешённых моделях | W2 |
| Заметки оператора и оркестратора | `notes`: CLI-команда `cmr note add` пишет импорт из одной заметки | W2 |
| Собственные прогоны оценки | `evalrun`: JSON-результаты внутренних наборов оценки | этап B |
| Исходы запусков из task-board: вердикты ревью, приёмка, круги доработки по роли, модели и уровню | `outcomes`: потребляет записи обратной связи из R12 | после W5 |
| Внешние лидерборды, предоставленные оператором согласно их условиям | по одному импортёру на каждый; любой API-ключ принадлежит хосту и никогда не попадает в запись | позже |

**Без сети в импортёрах.** Импортёр читает файлы или скомпилированные данные модуля и никогда ничего не скачивает. Скачивание внешнего источника, где оно есть, — отдельная команда хоста, чей вывод — файл.

## 7. Хранилище

- **Корень.** Корень хранилища — явный параметр. W2 решает его значение по умолчанию в раскладке данных Curator и записывает, почему.
- **Раскладка:**
  - `imports/<digest>.json`: неизменяем;
  - `snapshots/<digest>.json`: неизменяем;
  - `views/<view-id>.json`: представление пригодности для ролей, с ключом по всем его входам (§4);
  - `current`: дайджест текущего снимка, заменяется атомарным переименованием.
- **Параллельный доступ.** Писатели берут эксклюзивную (`O_EXCL`) блокировку рядом с `current`. Читателям блокировка не нужна, потому что каждый файл, который они читают, неизменяем.
- **CLI для просмотра** (`cmr`), каждая команда с `--json`:
  - `cmr evidence import FILE`
  - `cmr evidence ls`
  - `cmr evidence show ID`
  - `cmr evidence unresolved`
  - `cmr note add` / `cmr note retract`
  - `cmr suitability --role ROLE`

## 8. Приёмка (поток W2)

1. **Канонический круговой проход.** Импорт, каноникализация и дайджест стабильны между запусками и платформами. Тестовые векторы закоммичены.
2. **Паритет Bug Hunt.** Импортёр `bughunt` воспроизводит каждую бенч-строку зафиксированной версии модуля, с сохранением `evidence_kind` и стоимости. Табличный тест падает, если модуль добавляет строку, которую импортёр пропускает.
3. **Точность уровня.** Наблюдение с неизвестным уровнем никогда не сопоставляется кандидату. Перенесённое значение без правила отклоняется.
4. **Неразрешённые модели.** Неразрешённая модель сохраняется, фиксируется в отчёте и никогда не сопоставляется.
5. **Жизненный цикл записей.**
   - Заметка после `review_by` весит ноль при замороженном `evaluated_at`.
   - Замена и отзыв — только добавлением, а активное множество не зависит от порядка импортов.
   - Тестовые векторы покрывают: цепочку C → B → A; отзыв её головы (B оживает); отзыв её середины (A оживает); двойную замену (`evidence_conflict`); цикл, который отклоняет свой импорт.
6. **Расчёт.** Расчёт пригодности для ролей детерминирован и воспроизводим, а его вклады складываются в его градацию. Тестовые векторы покрывают категорию без свидетельств (`unknown`), категорию только с заметками, частичное совпадение отпечатка `partial` и два проекта с разными требованиями: их представления различаются.
7. **Герметичные тесты.** Тесты не используют сеть, работают во временном корне хранилища и запускаются с `-race`.
