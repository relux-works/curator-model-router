# Локальные модели: точные веса и их оценки

Простыми словами о том, как роутер оценивает локальные модели и почему оценка привязана к конкретному файлу весов.
Подробная спецификация: [spec/recommend.md](../spec/recommend.md) и [формат документа способностей](local-capability.md).

> **Статус реализации.** Этот репозиторий содержит офлайн-роутер и инструменты работы с данными оценок. Проверка файла движком при
> импорте и загрузке, поля схемы локальных конфигов, передача отпечатка через task-board и его запись в запуск — **запланированная
> интеграция** в других компонентах. Роутер проверяет переданные идентификаторы и оценки, но не проверяет, какой файл загружен.

## Проблема

Локальная модель — это файл на диске, например `qwen-3.8-27b-Q4_K_M.gguf`. Под одним названием «Qwen 3.8 27B» живут разные файлы:

- с разной квантизацией: Q4 сжата сильнее и обычно работает хуже, Q8 точнее;
- из разных сборок и конвертаций;
- с разным шаблоном чата или токенизатором.

Если оценивать модель «по названию», оценка одного файла незаметно применится к другому. Например, роутер решит, что Q4 так же хороша, как Q8. Или под тем же именем после перекачки запустится уже другой файл, и в истории это не будет видно.

## Решение: отпечаток файла

Для каждого файла весов считается отпечаток — хэш SHA-256 всего файла:

```text
gguf-sha256:3f9a0c…(64 шестнадцатеричных символа)
```

- Тот же файл всегда даёт тот же отпечаток, где бы он ни лежал и как бы ни назывался.
- Изменение хотя бы одного байта даёт другой отпечаток.
- Отпечаток охватывает данные токенизатора и шаблон чата, если он встроен в GGUF. Переопределения при запуске, например внешний шаблон
  чата, не меняют отпечаток файла; оператор должен отдельно проверить их совместимость с оценкой.

Первая версия поддерживает только один неразбитый GGUF-файл. Для MLX, разбитых GGUF и адаптеров позже появятся свои префиксы.

## Как это работает, по шагам

Шаги 1–3 — планируемая интеграция движка и конфигов; шаги 4–5 реализованы в роутере.

1. **Импорт файла (движок).** Когда файл весов добавляют в движок, движок считает отпечаток и записывает его в свою запись в
   `~/.curator/engines.toml`: «у движка `local-qwen` файл с отпечатком `3f9a…`».
2. **Разрешение оператора (закрепка).** В вашем локальном конфиге `~/.curator/runtimes.toml` у строки модели стоит
   `expected_weights_id`. Это значит: «под этим именем разрешаю только этот файл». Закрепка обязательна для каждой локальной модели.
3. **Запуск.** Движок открывает файл, пересчитывает отпечаток и сверяет три значения:
   - разрешённый (закрепка);
   - записанный при импорте;
   - фактический (файл, который реально открыт).

   Если хоть одно не совпало — запуск должен отказать с понятной ошибкой и всеми тремя значениями. Эту проверку выполняет движок или
   клиент; решение роутера само по себе не доказывает, какой файл был загружен.
4. **Оценка (роутер).** Роутер знает, насколько хороши эти веса, одним из двух способов:
   - **перенос:** берётся публичная оценка базовой (неквантованной) модели и умножается на коэффициент квантизации, например «Q4 примерно
     на столько-то хуже». Это приблизительная оценка, и её погрешность намеренно расширена;
   - **замер:** тесты прогнали на этом самом файле. Для одной оси качества и применимой области задач замер точного файла имеет
     приоритет над переносом.

   Оценка применяется, только если совпадают **и отпечаток файла, и режим рассуждений** (reasoning). Эта версия оценивает только
   `thinking=on` с точно совпадающей известной меткой reasoning effort. Контексты с выключенным thinking или неизвестными значениями
   остаются без оценки.
5. **Нет оценки — нет автовыбора.** Если для файла нет подходящей оценки, модель считается неоценённой. Роутер сам её не выберет.
   Для одиночного запуска явная фиксация agent, model и effort (включая буквальное `none`, где применимо) может вернуть допущенного
   неоценённого кандидата с учётом ограничений и жёстких правил политики. Решение сохраняет статус «без оценки»; для выполнения всё
   ещё нужны проверенные веса, закрепка и режим рассуждений.

## Ваш локальный конфиг

`~/.curator/runtimes.toml` — файл на каждой машине, в репозитории его нет. Каждый разрешённый файл весов получает **своё имя
модели** и свою закрепку. Предлагаемый конфиг (поле ещё не в схеме; сокращённые отпечатки — условные обозначения, а не допустимые
идентификаторы):

```toml
[runtimes.local-qwen.models."qwen-3.8-27b-q8"]
expected_weights_id = "gguf-sha256:3f9a…"   # файл Q8

[runtimes.local-qwen.models."qwen-3.8-27b-q4"]
expected_weights_id = "gguf-sha256:b71c…"   # файл Q4
```

Почему отдельные имена, а не список файлов под одним именем:

- у Q4 и Q8 разные оценки, и роутер должен видеть их как два разных варианта, чтобы выбирать по качеству и цене;
- в разрешениях task-board и в записи запуска сразу видно, какой файл работал;
- добавить ещё один вариант — это добавить ещё одну строку.

Если байты файла изменились (перекванчили, сконвертировали), меняется и отпечаток. Оператор должен передать новую закрепку и применимые
данные оценки для нового отпечатка; старая оценка к новому файлу сама не переносится. Перезакрепление одной командой и проверка при запуске —
запланированная интеграция; этот CLI их не предоставляет. Повторная загрузка тех же байтов отпечаток не меняет.

## Откуда берутся оценки

- **Базовые модели.** Сначала из публичных источников, для которых не нужны ключи (выгрузка лидерборда в файл, команда
  `cmr local import-base`). Источники подключаемые: позже можно добавить провайдеров, которым нужен ключ. Ключ никогда не попадает в
  записи и решения.
- **Коэффициенты квантизации** задаёт оператор (`cmr local coefficients` проверяет таблицу). Опубликованные данные KLD/perplexity
  llama.cpp или парные замеры могут служить основой, но оператор указывает калибровку, погрешность и срок действия для каждого точного
  файла. Библиотека стартовых коэффициентов не содержит; применимые замеры точного файла главнее переносов.
- **Замеры** содержат идентификатор данных оценки, ось качества, контекст рассуждений, область задач и измеренную оценку (значение 0–100,
  стандартная ошибка, источник и дата). Внешняя запись материализации указывает точные веса и квантизацию и может ссылаться на базовую
  модель. Число наблюдений обязательно для review и необязательно для остальных осей. Набор тестов, харнесс и рецепт описываются в
  сведениях о происхождении; отдельных полей для них нет.

Этот функционал оценки локальных весов не содержит готовых коэффициентов квантизации или новых сторонних оценок. Данные для оценки
локальных весов предоставляет оператор; существующий встроенный каталог содержит сторонние бенчмарк-оценки облачных моделей.

## Кто за что отвечает

| Часть | Что делает |
| --- | --- |
| Движок (curator-engines), планируется | считает отпечаток при импорте, пересчитывает и сверяет его при каждом запуске, сообщает фактический режим рассуждений |
| Схема файлов `~/.curator` (agents-management), планируется | описывает, где хранятся отпечаток (`engines.toml`) и закрепка (`runtimes.toml`), и проверяет их формат |
| task-board, планируется | передаёт отпечаток и режим рассуждений каждого локального кандидата в роутер и записывает их в запись запуска |
| Роутер (эта библиотека) | применяет оценку только к точному файлу в нужном режиме, а неоценённые модели в автовыбор не пускает |

## Чего это не делает

- Не защищает файл от подмены тем же пользователем на диске. Для выполнения нужна отдельная проверка закрепки, открытого файла и
  фактического режима рассуждений движком или клиентом. Решение роутера не доказывает, какой файл был загружен.
- Не делает выводов о модели по её названию. Название — только ярлык, правду говорит отпечаток.
